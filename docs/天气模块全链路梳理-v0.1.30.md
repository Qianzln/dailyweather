## 0. 结论速览

| 项 | 结论 |
|---|---|
| 架构 | 单 Activity + Compose，手写 DI（`AppContainer`），DataStore 承载全部持久化 |
| 数据源 | App **零 Key**：唯一出口是 CloudBase 云函数 `weatherProxy`（与「微风天气」共用同一函数） |
| 主源 | **小米 wtr-v3**（主）+ **彩云 v2.6**（补短临/预警/逐时概率）。⚠️ README 与路线图仍写「彩云主源 + 和风/小米备源」，**已过时** |
| 数据模型 | 三源统一归一化为 `WeatherSnapshot`，缓存落 `SnapshotCodec` JSON + 来源标签，下游（UI/组件/通知）对上游无感 |
| 刷新模型 | 单派生源：`RefreshManager` → `WeatherRepository` → DataStore；UI 由 Flow 驱动 |
| 组件/通知 | 旁路轮询（WorkManager），**刷新成功不联动推送组件与胶囊**，最多滞后 30 分钟 |
| 主要缺口 | ①`POST_NOTIFICATIONS` 从不申请也从不检测 ②Worker 永不重试 + 无网络约束 ③超时常量为死代码 ④台风/预警/雷达数据已解析但无 UI |
| 可运行性 | **当前源码编译通过**（`compileDebugKotlin` → `BUILD SUCCESSFUL in 39s`，仅 5 处 warning）；但磁盘上的 debug APK 落后于源码，需重新构建。详见 §8 |

## 1. 数据来源与获取方式

### 1.1 链路总览

```
        ├── XiaomiProvider    (主源)  data/remote/Providers.kt:70-419

        ↓

        ↓  唯一外部网络出口

        ↓
小米 weatherapi.market.xiaomi.com/wtr-v3 · 彩云 api.caiyunapp.com · 高德 restapi.amap.com
```

**关键点：APK 内不含任何上游凭据。** 云函数把 Key 放在环境变量里
（`CAIYUN_APP_KEY` / `CAIYUN_APP_SECRET` / `AMAP_WEB_KEY` / `QWEATHER_API_KEY`，
见 `index.js:127-128,168,187,580`），客户端只持有云函数 URL
（`BuildConfig.CLOUDBASE_PROXY_URL`，来自 `keys.properties`，已 gitignore –
`app/build.gradle.kts:40`）。

### 1.2 各数据源明细

| 源 | 角色 | 客户端路由 | 云端上游 / 说明 |
|---|---|---|---|
| 小米 wtr-v3 | **主源** | `/weather/xiaomi-geo` → `/weather/xiaomi`（两步） | `index.js:592`；一次给全实况 + 逐时 + 逐日 + AQI 六项 + 台风，**不随 days 截断** |
| 彩云 v2.6 | **辅源** | `/weather/caiyun`（`alert=true&dailysteps=7&hourlysteps=48`） | `index.js:120,138`；HMAC 签名在云端（`index.js:127-145`），BYOK 可选 |
| 高德 Web 服务 | 地理 | `/geo/amap-regeo`（逆地理四级名）、`/geo/amap-district`（城市搜索） | `index.js:167-200`；进高德前做 WGS-84→GCJ-02（`util/CoordinateTransform.kt`） |
| 和风天气 | **已弃用** | `/weather/qweather-now|7d|72h` 路由仍在云函数里 | `index.js:157-159`；App 侧已无 provider 引用（`ProviderChain.standard` 只有两项） |
| RainViewer 雷达 | 未接线 | `/radar/meta|frame|coverage` | `index.js:278-279`；`RadarGateway` 已写但**无任何调用点** |

### 1.3 主源选型理由（代码注释已写明，`Providers.kt:55-69`）

- 小米一次给全：实况 + 逐小时 + 逐日 + AQI 六项，且不被 `days` 截断；
- `appKey`/`sign`/`locale` 是社区公开常量，由云函数内置，APK 零凭据；
- `isGlobal` 由云函数按 locationKey 前缀推导，客户端不可伪造。

彩云降为辅源的原因（`Providers.kt:26-27`）：共享 Key 的 `dailysteps` 硬上限 3 天且静默截断，
逐日不可依赖。彩云只补三样小米给不了的东西：**分钟级短临描述、气象预警、逐小时降水概率**。

### 1.4 融合策略（非「谁先成功用谁」）

`WeatherRepository.refresh()` 顺序执行 provider 列表，第一个成功者作 base，
后续源用 `mergeGaps()` **只补空字段、不覆盖已有值**（`WeatherRepository.kt:82-112`）：

- 逐小时：base 全为 0 概率时，按**下标对齐**从辅源拷贝 `precipitationProbability` / `aqi`
- 逐日：取条数多的那份（小米 7+昨天 vs 彩云 3）
- 实况：aqi/pm25 为 0 时补，`airQualityDesc`/`comfortDesc` 空串时补
- `minutely`：base 为 null 才取辅源
- 全部源失败 → `throw IllegalStateException("全部天气源失败…")`（`:75`）

⚠️ **下标对齐是隐患**：小米与彩云首点时间戳未必一致，`extra.hourly.getOrNull(i)`
可能与 `base.hourly[i]` 不是同一小时，导致降水概率/逐时 AQI 串位。

### 1.5 云端缓存

云函数内进程级缓存（`index.js:684-697`）：彩云/小米综合 **5 min**、
xiaomi-geo **6 h**、amap-regeo **6 h**、amap-district **24 h**。
同 IP 高频请求会被函数缓存吸收，App 端 30 分钟周期的实际上游压力很小。

### 1.6 App 侧异常兜底

- `CloudProxy` 未配置 → `require(isConfigured)` 抛错 → `ProxyNotConfiguredException`
  → `DataSourceNotConfiguredException` → UI 显示降级文案，不崩（`CloudProxy.kt:37,44`）
- 单次 HTTP 超时 10 s（`CloudProxy.kt:87`，connect + read 各自 10 s）
- 刷新失败**不覆盖**缓存：`putSnapshot()` 只在成功路径调用（`WeatherRepository.kt:76`），
  DataStore 旧快照保留 → 组件/通知仍能出数（但无「数据已过期」标记）

## 2. 数据结构与字段定义

### 2.1 主模型 `WeatherSnapshot`

定义：`app/src/main/java/com/dailyweather/app/data/model/WeatherSnapshot.kt:10-120`

| 顶层字段 | 类型 | 说明 |
|---|---|---|
| `cityId` | String | 城市 ID（定位城市固定 `"current"`） |
| `fetchedAt` / `serverTime` | Long | 本地抓取时间 / 上游服务器时间（ms） |
| `forecastKey` | String | 一句话预报（Hero 副行 + 通知正文用） |
| `realtime` | `Realtime?` | 实况 |
| `minutelyDesc` | String | 短临描述（独立字段，与 `minutely.description` 并存） |
| `minutely` | `Minutely?` | 未来 2 h 逐分钟降水（120 值） |
| `hourly` | `List<HourlyPoint>` | 逐小时 |
| `daily` | `List<DailyPoint>` | 逐日（小米源首行是「昨天」） |
| `alerts` | `List<AlertItem>` | 气象预警（仅彩云提供） |
| `typhoons` | `List<Typhoon>` | 活跃台风（仅小米提供） |

**内容签名** `contentSignature()`（`:27-32`）= 实况温度 + 实况 skycon + 小时首点温度 + 日卡首点日期。
组件按此签名做「未变则跳过重绘」。

#### Realtime（`:33-53`）
`temperature` / `apparentTemperature` / `humidity`(0-1) / `skycon` / `windSpeed`(km/h) /
`windDirection`(度) / `aqi` / `pm25` / **`pm10` `o3` `no2` `so2` `co`**（0 = 上游没给）/
`uvIndex` / `comfortDesc` / `airQualityDesc` / `pressureHpa` / `visibilityKm`

#### HourlyPoint（`:55-64`）
`time`(epoch ms) / `temperature` / `skycon` / `precipitationProbability`(0-100) /
`precipitationMm` / `aqi`

#### Minutely（`:67-71`）
`description` / `precipitation2h: List<Double>`（120 个值，照上游 mm/h 原值）

#### DailyPoint（`:73-87`）
`date`("yyyy-MM-dd") / `skycon` / `tempMin` `tempMax` / `windSpeed` `windDirection` /
`sunrise` `sunset`("HH:mm") / `uvIndex`(**Int**) / `aqiAvg` / `precipitation`(mm) /
`precipitationProbability`(0-100)

#### AlertItem（`:89-95`）
`title` / `status` / `description` / `source` / `pubTime`(epoch ms)

#### Typhoon / TyphoonPoint（`:98-116`）
`typhoonId` `name` `currentLat/Lon` `windSpeedKmh` `pressureHpa` `moveSpeedKmh`
`moveDirection` + `path: List<TyphoonPoint>`

### 2.2 解析器

| 上游 | 类 / 位置 | 要点 |
|---|---|---|
| 彩云 v2.6 | `CaiyunParser` `WeatherSnapshot.kt:122-258` | 先剥 `result` 包裹；`hourly.precipitation[].probability` 是小时降水概率的**真实来源**（`:159-167`）；`daily.temperature[].min/max`；ISO 时间用 `OffsetDateTime.parse` |
| 小米 wtr-v3 | `XiaomiProvider.parse` `Providers.kt:95-193` | 数值一律包在 `{value,unit}` 里且 **value 是字符串**；`current.weather` 是天气代码字符串，走 `WEATHER_TEXT` 码表（`:368-377`）；**单位不认就当缺失，不猜换算**（`:344-365`） |

**小米源的三个刻意口径**（代码注释明确，是踩坑记录）：
1. `forecastDaily.temperature[i].from` 是**最高温**、`to` 是最低温（`:287-288`）；
2. `forecastHourly` **没有降水概率** —— 该粒度填 0 表示「无此数据」，不拿逐日概率冒充（`:264-265`）；
3. 昼夜判定按**城市当地时间**：`LocalTime.now(zone)`，因为设备时区与城市不一致时 UTC 午夜会把白天判成夜（`:106-108`）；
4. `35 轻雾` 刻意降级到 `MODERATE_HAZE` 而不是 `FOG` —— 雾景会把天空钉成灰黄且不参与昼夜插值（`:379-384`）。

### 2.3 缓存编解码与来源标签

`SnapshotCodec`（`data/model/SnapshotCodec.kt`）做 `WeatherSnapshot ⇄ JSONObject` 全字段往返，
含 `typhoons`。落盘时额外挂 `source` 标签（`data/WeatherStore.kt:97-102`），
UI 底部署名行读它（`WeatherViewModel.sourceOf()` `:452-453`）。

存储键：`weather/<cityId>/raw`（JSON）+ `weather/<cityId>/ts`；城市表整包存 `cities_json`
（`WeatherStore.kt:121-126`）。阶段一用 Preferences DataStore，路线图 P1 计划换 Room。

### 5.4 数据一致性 / 时区缺陷

1. **`PrecipCard` 用设备时区而非城市时区**：`WeatherScreen.kt:943` 写死
   `ZoneId.systemDefault()`，而 `HourlyCard` 用传入的 `zone`（`:525/538`）。
   跨时区看城市时，降水卡首尾钟点与小时卡不一致。
2. **`HeroSection` 的「今天」用设备时区**：`:462` 用 `LocalDate.now()`（无 zone），
   而 `DayRow` 用 `LocalDate.now(zone)`（`:625`）—— 两个口径不一致。
3. **单位切换不主动触发重组**：`Units` 字段是普通 `@Volatile var` 而非 Compose `State`
   （`data/Units.kt:17-21`）。不切页改单位时首页不会重组，靠返回导航重建才刷新。
4. **`mergeGaps` 按下标补字段**：见 §1.4，首点时间未对齐时会串位。

### 5.5 组件 / 通知侧缺陷

1. **`POST_NOTIFICATIONS` 从不申请也从不检测**（最严重）：
   Manifest 声明了（`AndroidManifest.xml:9`），但 `MainActivity` 只申请定位权限
   （`MainActivity.kt:67-69`）；`NotificationChannels.enabled()`
   （`Notifications.kt:52-59`）**只看渠道 importance**，
   检测不到 App 级权限被拒 → Android 13+ 上 Worker 以为能发、实际被系统吞掉。
2. **刷新成功不联动组件与胶囊**：`onRefreshSuccess` 只入队预警检查
   （`di/AppContainer.kt:56-68`），没有触发 `WidgetSyncWorker` 或胶囊 → 下拉刷新后
   桌面组件最多滞后 30 分钟。
3. **所有 Worker 恒 `Result.success()`**：唯一 `Result.failure()` 在
   `WidgetSyncWorker.kt:39`（强转失败）。业务失败被 `RefreshManager` 吞成
   `Outcome.Failed`（`:66-72`），Worker 无从知晓 → **永不重试**，且无 `setBackoffCriteria`。
4. **全部周期任务无 Constraints**：全项目 0 处 `NetworkType` / `requiresCharging` /
   `requiresBatteryNotLow` —— 离线时也照跑一轮再等 30 分钟。
5. **双重 30 分钟调度**：8 个 `weather_widget*_info.xml` 全是
   `updatePeriodMillis=1800000`，与 WorkManager 周期（`WidgetSyncWorker.kt:129`）
   共同触发 `onUpdate → enqueueOneTime`，靠签名去重兜住，属冗余。
6. **`DailyWeatherApp.kt:45` 无条件 `enqueuePeriodic`**：抵消了
   `cancelIfNoInstances()`（`WidgetSyncWorker.kt:133-145`）的清理效果 ——
   没放任何组件也会一直跑 30 分钟同步。
7. **`lastSignatures` 进程级 `mutableMap`**（`WidgetSyncWorker.kt:25`）：非线程安全、
   组件移除后 key 不清理（内存泄漏）。
8. **早晚报时刻会漂移**：`PeriodicWorkRequest(24, HOURS)` + `initialDelay` 只在**首次**
   保证 7:30/19:30；之后按 24 h 从上次执行点滚动。
9. **`PersistentWeatherWorker` 缺渠道/权限守门**：另两条通知线都有
   `NotificationChannels.enabled()`，胶囊线（`Notifications.kt:287-311`）直接 `post()`。
10. **`AlertDedup` 修剪可能误删**：`merged.drop(merged.size - MAX_KEYS)`
    （`Notifications.kt:266`）对 Set 迭代顺序无保证，可能裁掉较新的 key。
11. **Android 16 升格依赖反射**改 `Notification.flags`（`Notifications.kt:90-95`），
    脆弱且要求 API 36。

## 6. 天气更新的推送机制

### 6.1 触发时机

| 触发点 | 入口 | 注册位置 |
|---|---|---|
| App 冷启动 | `maybeColdStartRefresh()` → `refreshDefault("app_cold_start")` | `WeatherViewModel.kt:233-240` |
| 定位位移（>500 m） | `startMoveWatcher` → `refreshCurrentLocation("location-moved")` | `WeatherViewModel.kt:201-206` |
| 手动下拉刷新 | `refreshCurrent()` → `refresh(id, "app_home_refresh")` | `WeatherViewModel.kt:256-272` |
| 点定位按钮 | `locateAndRefresh()` | `WeatherViewModel.kt:279-297` |
| 添加城市 | `addCity()` → `refresh(cityId,"city_added")` | `WeatherViewModel.kt:303-317` |
| 桌面组件系统刷新 | `onUpdate()` → `enqueueOneTime("widget_update")` | `widget/WeatherWidgetProviders.kt:10-12` |
| 组件首个实例放置 | `onFirstInstance()` → `enqueuePeriodic + enqueueOneTime` | `WeatherWidgetProviders.kt:14-16`、`WidgetSyncWorker.kt:185-189` |
| 预警检查（事件驱动） | `onRefreshSuccess` → 一次性 `urgent_alert_check` | `di/AppContainer.kt:56-68` |

**无 AlarmManager**，「定时」全部靠 WorkManager。

### 6.2 更新频率

| 任务 | 唯一名 | 间隔 | 位置 |
|---|---|---|---|
| 组件同步 | `weather_widget_periodic` | **30 min** | `WidgetSyncWorker.kt:125-131` |
| 常驻胶囊 | `weather_notification_periodic` | **30 min** | `DailyWeatherApp.kt:47-51` |
| 每日早报 | `daily_weather_morning` | **24 h**（初延迟到 07:30） | `Notifications.kt:171-174` |
| 每日晚报 | `daily_weather_evening` | **24 h**（初延迟到 19:30） | `Notifications.kt:175-178` |
| 系统组件刷新 | — | **30 min**（`updatePeriodMillis`） | 8 个 `res/xml/weather_widget*_info.xml:5` |
| 预警检查 | `urgent_alert_check` | 事件驱动，非周期 | `AppContainer.kt:58-66` |

约束：**无任何 Constraints、无抖动、无退避策略**。

### 6.3 推送渠道

| 通知 | 渠道 ID / 重要度 | 通知 ID | 内容字段 |
|---|---|---|---|
| 早报 / 晚报 | `daily_forecast` / DEFAULT | `1002` / `1003` | `currentTemp`、`currentSkycon`、`daily[0].tempMin/Max`、`forecastKey.take(40)`；`BigTextStyle` |
| 气象预警 | `weather_alerts` / HIGH | `1004 + i`（单轮 ≤3 条） | `AlertItem.title` / `description.take(80)` |
| 常驻胶囊 | `weather_live` / MIN | `1001` | `currentTemp`、`currentSkycon`、`forecastKey.take(30)`；`setOngoing` + `setSilent` |

渠道创建：`NotificationChannels.ensureAll()`（`Notifications.kt:38-50`），在
`DailyWeatherApp.onCreate` 调用（`:30`）。

**数据来源全部是缓存**（`weatherRepository.cached()`），**不是当场请求** ——
所以推送时效取决于最后一次成功刷新。

**「划除后 6 小时静默」**：
`setDeleteIntent` → `LiveUpdateDismissReceiver`（`:113-120`）写
`liveUpdateSuppressedUntil = now + 6h`（DataStore key `weather_live_suppressed_until`），
`PersistentWeatherWorker` 在 `:298` 读它并跳过。

### 6.4 失败重试与异常处理

```
provider.fetch() 抛错
   → WeatherRepository 捕获，记 errors，continue 下一个源（:61-64）
   → 全部失败 → throw IllegalStateException（:75）
   → RefreshManager 捕获（:69-72）→ Outcome.Failed(reason)
   → ViewModel 把 reason 显示到 vm.message（首页提示卡）
   → Worker 侧：RefreshManager 不抛异常给 Worker → Worker 照常 Result.success()
```

结论：**失败不重试、不退避、不改 WorkManager 状态**；用户可见的唯一反馈是首页 `vm.message`。
隐性兜底是「失败不覆盖缓存」，组件/通知继续用旧快照。

### 6.5 刷新后的一致性传播

| 消费方 | 机制 |
|---|---|
| UI | DataStore Flow → `WeatherViewModel.snapshots` → `collectAsState`（响应式，即时） |
| 桌面组件 | `AppWidgetManager + RemoteViews`（非 Glance）；**仅靠自身 30 min 周期触发** |
| 通知 | 各自 Worker 重读缓存重绘；**仅靠自身周期触发** |

## 9. 改进建议（按优先级）

### P0

1. **补通知权限运行时申请**：`MainActivity` 加 `RequestPermission(POST_NOTIFICATIONS)`
   （API 33+），并在每个 Worker 里用
   `NotificationManagerCompat.from(ctx).areNotificationsEnabled()` 替代/补充渠道检测；
   `NotificationChannels.enabled()` 内同时检查 App 级权限。
2. **刷新成功联动组件与胶囊**：`onRefreshSuccess` 里追加
   `WidgetSyncWorker.enqueueOneTime(ctx, "refresh_success")` +
   一次性 `PersistentWeatherWorker`，让三端数字一致。
3. **给周期任务加约束与退避**：`setConstraints(NetworkType.CONNECTED)`；
   把业务失败透出为 `Result.retry()` + `setBackoffCriteria(EXPONENTIAL, 30s)`。

### P1

4. **让超时常量真正生效**：在 `WeatherRepository.refresh()` 的 provider 循环外包
   `withTimeout(WEATHER_FETCH_TOTAL_TIMEOUT_MS)`，单次 `withTimeout(ATTEMPT)`。
5. **按时间戳而非下标合并逐小时**：`mergeGaps` 改为按 `hourly[i].time` 最近邻匹配。
6. **补齐或删除承诺的功能**：
   - 二选一：实现台风详情页（数据已齐）与首页预警卡；或从 `HomeCardId` 移除 `RADAR`
     并改掉其标题文案，避免「承诺但无实现」。
   - 三个空转开关：要么实现（温度骤变 / 大风 / 极端天气阈值检测），要么从设置页移除。
7. **修正名不符实**：`SHOW_HOURLY48` 要么真渲染 48 条，要么改名 + 改文案；
   日卡 `take(5)` 与「7 日」注释 / Tokens 命名对齐（数据层小米已给 7 天，改为 7 只需一行）。

### P2

8. 统一时区口径：`PrecipCard` 接收 `zone` 参数；`HeroSection` 用 `LocalDate.now(zone)`。
9. `Units` 换成 `mutableStateOf`（或包一层 Compose State）以支持即时重组。
10. `DailyWeatherApp.kt:45` 改为「有实例才注册」，让 `cancelIfNoInstances` 真正生效。
11. `lastSignatures` 换成 `ConcurrentHashMap`，并在组件删除时清理对应 key。
12. `AlertDedup` 修剪改为按写入时间淘汰（存 `key→timestamp`），避免误删新 key。
13. 早晚报改用「每日固定时刻」调度（一次性任务执行后自行排下一天），消除 24 h 漂移。
14. `PersistentWeatherWorker` 补渠道/权限守门，与另两条通知线一致。
15. 明确架构归属：`weatherProxy` 为两个 App 共用，建议在云函数里按调用方
    （UA 或 path 前缀）隔离应用更新通道，避免互相串版本。
